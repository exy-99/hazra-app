The exact SQL for the upsert:
```sql
INSERT INTO attendance (id, worker_id, date, status, note, updated_at)
VALUES (?, ?, ?, ?, ?, ?)
ON CONFLICT(worker_id, date) DO UPDATE SET
  status = excluded.status, note = excluded.note, updated_at = excluded.updated_at;
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI tap → attendance row | Rapid taps and status changes cross into the write path |
| note text → SQLite | Free-text note crosses into SQL |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigate |
|-----------|----------|-----------|-------------|----------|
| T-06-01 | Tampering | duplicate attendance rows | mitigate | Single-statement `INSERT ... ON CONFLICT(worker_id, date) DO UPDATE` backed by the `UNIQUE(worker_id,date)` constraint (plan 01-04). |
| T-06-02 | Tampering / SQL injection | note/date/workerId | mitigate | All values are bound `?` parameters. |
| T-06-03 | Tampering | invalid status | mitigate | TS union + SQL `CHECK(status IN (...))`; the DAO never builds status strings dynamically. |
| T-06-04 | Repudiation | lost correction | mitigate | `updated_at` is rewritten on every upsert so the last write is authoritative and auditable. |
| T-06-05 | Information disclosure | inactive workers leaking into date view | mitigate | `WHERE w.is_active = 1` in `getAttendanceForDate`/`getDailyCounts`; history still reachable via `getAttendanceForWorker`. |
</threat_model>
