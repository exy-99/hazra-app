<objective>
Establish push navigation for all drill-down screens by moving the four tab routes into a `(tabs)` group and rendering a root `Stack`, without changing launch behavior or URLs.

Purpose: the root layout currently renders only `NativeTabs`, so drill-down routes (`/worksites`, `/worksite-form`, `/worker-form`, …) have no Stack to push on. Per the versioned Expo docs, "you should nest a native `<Stack />` layout inside the native tabs to support both headers and pushing screens" — the standard shape is a root Stack hosting a `(tabs)` group (route groups are URL-transparent, so `/workers` keeps working). Every later Phase 2 plan depends on `router.push` actually presenting a screen with a back arrow (design.md §8).
Output: `(tabs)` group with four moved tab routes, a tabs group layout, and a root Stack layout with titled drill-down screens.
</objective>

Expo docs (native-tabs, verified 2026-10-05 against SDK 57 page): "The JavaScript `<Tabs />` have a mock stack header which is not present in the native tabs. Instead, you should nest a native `<Stack />` layout inside the native tabs to support both headers and pushing screens." Docs search-group example: root `_layout.tsx` holds `<NativeTabs>` triggers pointing at a `search/` directory whose own `_layout.tsx` renders `<Stack />`. This plan inverts that (root Stack + `(tabs)` group) which is the same sanctioned composition and keeps drill-down URLs flat (`/worksites`, not `/workers/worksites`).

DO NOT change any of this logic — only swap `<AppTabs />` for `<Stack>`.

`AppTabs` triggers (unchanged by this plan): names `index`, `attendance`, `workers`, `reports`. These resolve group-relatively once rendered from `(tabs)/_layout.tsx`; URLs are unchanged because `(tabs)` is URL-transparent. Web layout (`app-tabs.web.tsx`, expo-router/ui) needs no change.
