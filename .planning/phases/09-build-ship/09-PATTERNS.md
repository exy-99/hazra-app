### `eas.json` (config, batch)

**Analog:** none. The repository has no existing EAS configuration; use the researched current EAS schema rather than extrapolating from another local JSON file.

**Authoritative upstream contract** (`09-RESEARCH.md` lines 97-114):

```json
{
  "cli": {
    "version": ">= 27.4.1",
    "appVersionSource": "remote",
    "requireCommit": true
  },
  "build": {
    "production": {
      "credentialsSource": "remote",
      "android": {
        "buildType": "apk",
        "autoIncrement": "versionCode"
      }
    }
  }
}
```

**Apply this pattern exactly:**

- Keep one profile named `production`; do not add development, preview, Play/AAB, iOS, web, submit, or update profiles.
- `android.buildType: "apk"` is mandatory; an empty/default production profile would produce an AAB.
- Use `cli.appVersionSource: "remote"` with Android `autoIncrement: "versionCode"`; do not implement a local counter.
- Use remote credentials. Do not add credential paths, passwords, keystore data, environment secrets, or a local `credentials.json` reference.
- Keep `requireCommit: true` so the user's H3 build is tied to committed source.
- Do not use `distribution: "internal"`, `gradleCommand`, `channel`, `releaseChannel`, or submit/update configuration.

**Auth/guard boundary:** EAS login, project choice/linking, credential interaction, and build invocation are external privileged actions. This file declares a profile only; it must not automate those actions.

**Validation convention:** parse it locally in `verify-release-config.mjs`. Schema resolution through `npx eas-cli@latest config ...` belongs to the user's linked-project checkpoint and must not be represented as completed in advance.

### `scripts/verify-release-config.mjs` (test, batch + file-I/O)

**Analog:** `scripts/verify-app-assets.mjs`

**Imports and synchronous root-file parsing pattern** (`scripts/verify-app-assets.mjs` lines 1-8):

```javascript
// Standing gate for plan 08-07: app.json icon/splash wiring.
// Run: node scripts/verify-app-assets.mjs
import { existsSync, readFileSync } from 'node:fs';

const config = JSON.parse(readFileSync('app.json', 'utf8')).expo;
const splash = (config.plugins || []).find(
  (plugin) => Array.isArray(plugin) && plugin[0] === 'expo-splash-screen'
);
```

**Assertion and reporting pattern** (`scripts/verify-app-assets.mjs` lines 10-17):

```javascript
let fail = false;
const ok = (pass, label) => {
  console.log((pass ? 'PASS' : 'FAIL') + ' ' + label);
  if (!pass) fail = true;
};
const eq = (actual, expected, label) => {
  ok(actual === expected, label + ' = ' + JSON.stringify(actual));
};
```

**Locked-key validation pattern** (`scripts/verify-app-assets.mjs` lines 49-58):

```javascript
// Keys that must never move while wiring assets.
eq(config.android?.package, 'com.exy99.hazraapp', 'android package');
eq(config.experiments?.typedRoutes, true, 'typedRoutes');
eq(config.experiments?.reactCompiler, true, 'reactCompiler');
for (const plugin of ['expo-router', 'expo-sqlite', 'expo-sharing']) {
  ok(
    (config.plugins || []).some((entry) => entry === plugin || (Array.isArray(entry) && entry[0] === plugin)),
    'plugin present: ' + plugin
  );
}
```

**Exit behavior** (`scripts/verify-app-assets.mjs` line 70):

```javascript
process.exit(fail ? 1 : 0);
```

**Copy/adapt these conventions:**

- Use dependency-free ESM and `node:fs`; read `app.json`, `eas.json`, and `.gitignore` synchronously from repository-root paths.
- Emit one visible `PASS`/`FAIL` line per contract assertion and aggregate failures so all drift is reported in one run.
- Let missing/malformed files throw naturally and make Node exit non-zero; existing standing gates do not hide parse errors with a broad `try/catch`.
- Validate the locked display/technical identity, real H1 owner and UUID shape, one production profile, remote source/credentials, APK output, `versionCode` auto-increment, no local `android.versionCode`, no submit block, and all required ignore rules.
- Also reject extra build profiles and release routes that violate scope. Do not call EAS, inspect credentials, download an APK, compute a checksum, or infer human results.
- The owner/UUID checks validate local shape only. Before H1, those assertions should remain unsatisfied rather than being bypassed with fabricated values.

**Testing convention:** run directly with `node scripts/verify-release-config.mjs`; do not add Jest/Vitest or a new test framework.

### `.planning/phases/09-build-ship/09-HANDOFF-TEMPLATE.md` (utility/documentation, file-I/O handoff)

**Analog:** none. No repository document is an APK install/update/checksum handoff guide. Use the locked Phase 9 research contract rather than copying the starter README or a phase summary.

**Checksum placeholder format** (`09-RESEARCH.md` lines 576-582):

```text
<64-hex-sha256> *Hazra-v1.0.0-build-<actualVersionCode>.apk
```

**Required template sections:**

1. **Release manifest placeholders:** Hazra `v1.0.0`, actual Android build number, package `com.exy99.hazraapp`, exact APK filename, byte size, EAS build ID, signing-certificate fingerprint, and SHA-256.
2. **Bundle contents:** APK, `INSTALL-AND-UPDATE.txt`, `RELEASE-MANIFEST.txt`, and `SHA256SUMS.txt`. Credential backups are explicitly excluded.
3. **Install instructions:** verify SHA-256, install the named APK through the approved private route, and launch the standalone app without Metro, Expo Go, or a development server.
4. **Future update instructions:** back up in Hazra first, verify the new checksum, then install the newer APK over the existing app. Never uninstall as a workaround because that removes local SQLite data.
5. **Mismatch instructions:** if Android reports a package/signature conflict or would require uninstalling, stop and contact the release custodian. Future APKs require the same application ID/signing key and a higher `versionCode`.
6. **Support/custody placeholders:** release custodian/support contact and non-secret archive reference only; never passwords, EAS tokens, keystore bytes, or credential-vault details.

The file remains a blank template. It may explain commands the user will run, but it must not claim that a checksum was generated, an APK was installed, a recipient received it, or a handoff succeeded.

## Shared Patterns

### 1. Continuous Native Generation

**Sources:** `AGENTS.md` lines 75-80; current `app.json`

Apply to `app.json` and `eas.json`: native release behavior is declarative. Never create or edit `android/` or `ios/`, and never add a custom Gradle release script for this phase.

### 2. Stable identity with remote build numbering

**Apply to:** `app.json`, `eas.json`, verifier, evidence template, handoff template

- Human-facing version: `1.0.0`.
- Installed label: `Hazra`.
- Stable technical identity: slug/npm name `hazra-app`, scheme `hazraapp`, package `com.exy99.hazraapp`.
- Android build number: actual remote `versionCode`, captured from the real completed build/APK by the user; never guessed or stored locally in app config.

### 3. Dependency-free standing gates

**Source:** `scripts/verify-app-assets.mjs` lines 3-17, 70

All repository contract checks use small direct Node `.mjs` scripts, synchronous reads, per-assertion `PASS`/`FAIL` output, and non-zero exit on drift. Do not introduce a test runner or package dependency.

### 4. Human-owned external checkpoints

**Apply to:** evidence and handoff templates, H1-generated `app.json` metadata

- H0-H7 are `autonomous: false` in downstream plans.
- The user owns EAS login/linking, credential selection/backup, build invocation, artifact download, binary inspection/checksum, installation, all device tests, second-device opening, and final handoff.
- Repo files provide constraints and blank fields only. No script should authenticate, configure credentials, invoke a cloud build, download an APK, mutate an APK, or manufacture evidence.

### 5. Immutable-artifact evidence chain

**Apply to:** release evidence and handoff templates

Every external fact must point to one source commit + EAS build ID + package/version pair + signing fingerprint + filename/size/SHA-256. Testing and delivery must use the same bytes. Any rebuild or source/config fix creates a new candidate and resets the complete matrix.

### 6. Secret and artifact separation

**Apply to:** `.gitignore`, evidence template, handoff template

Keystore/password-bearing recovery files stay in a user-controlled encrypted location outside Git and separate from the APK handoff. Evidence may record custodian, non-secret recovery reference, alias, and public certificate fingerprint, but never secret values.

### 7. Verification command conventions

**Repo-owned static gates:**

```powershell
node scripts/verify-release-config.mjs
node scripts/verify-app-assets.mjs
node scripts/verify-contrast.mjs
node scripts/verify-tab-shell.mjs
npx tsc --noEmit
npx expo-doctor
npx expo config --type public --json
git diff --check
git status --porcelain
```

The release verifier's owner/project-ID assertions become passable only after the user's H1 link metadata exists. `git status --porcelain` must be empty immediately before the user's H3 build because `requireCommit` is enabled. These commands prove repository/config health only; none proves a cloud build, signature, checksum, installation, physical-device behavior, or handoff.
